## 4. Data model

All tables have `id` (integer PK), `created_at` and `updated_at`. Every user-owned table has `user_id` (FK → `users.id`, `ON DELETE CASCADE`, indexed).

### `users`

| Column | Type | Notes |
| --- | --- | --- |
| email | varchar(255) | unique, stored lowercase |
| password_hash | varchar(255) | Argon2 |

### `categories`

| Column | Type | Notes |
| --- | --- | --- |
| user_id | FK | |
| name | varchar(100) | |
| kind | enum(`income`, `expense`) | |
| parent_id | FK → categories, nullable | `NULL` = top-level category; set = subcategory |

- `kind` is stored as a string (non-native enum, `income` / `expense`) with a CHECK constraint, so Postgres needs no `CREATE TYPE`.
- Unique on (`user_id`, `kind`, `parent_id`, `name`).
- Partial unique index `uq_categories_top_level_name` on (`user_id`, `kind`, `lower(name)`) `WHERE parent_id IS NULL`: the constraint above cannot stop duplicate top-level names because `NULL`s are distinct.
- Names are unique per level **case-insensitively** (`Food` = `food`): among a user's top-level categories of the same `kind`, and among the subcategories of one parent. The top level is enforced by the DB (index above) and the service; subcategories are enforced by the service (the DB constraint above is case-sensitive).
- Deleting a category deletes its subcategories (`ON DELETE CASCADE` on `parent_id`); deleting a user deletes their categories.
- Only two levels: a subcategory's parent must be top-level and of the same `kind` (validated in the service layer).
- Default set from plan.md §4.2 is created when the user registers, inserted in that order (parents before children), so ordering by `id` gives the §4.2 order. Income categories have no subcategories by default.

### `transactions`

| Column | Type | Notes |
| --- | --- | --- |
| user_id | FK | |
| type | enum(`income`, `expense`) | determines the sign |
| date | date | indexed together with `user_id` |
| amount | numeric(12,2) | `> 0`; for salary this is the **net** amount |
| gross_amount | numeric(12,2), nullable | only for income; `gross_amount ≥ amount` |
| category_id | FK → categories | top-level, `kind` must equal `type` |
| subcategory_id | FK → categories, nullable | must be a child of `category_id` |
| note | varchar(500), nullable | |

- `type` is stored like `categories.kind`: a string (non-native enum, `income` / `expense`) with the CHECK `ck_transactions_type`. It reuses the `CategoryKind` enum, so the service can compare `category.kind == type` directly.
- CHECK constraints: `ck_transactions_amount_positive` (`amount > 0`), `ck_transactions_gross_amount_gte_amount` (`gross_amount IS NULL OR gross_amount >= amount`) and `ck_transactions_gross_amount_income_only` (`gross_amount IS NULL OR type = 'income'`). The other rules in the table (category top-level and of the same `kind`, subcategory a child of it, ownership) are checked in the service layer.
- Indexes: `ix_transactions_user_id_date` on (`user_id`, `date`), which also covers the "`user_id` indexed" rule because `user_id` is the leading column; `ix_transactions_category_id` and `ix_transactions_subcategory_id`, for the "category in use" check and the FK checks when a category is deleted.
- The `category_id` / `subcategory_id` FKs are `NO ACTION` (no `ON DELETE`), not `RESTRICT` and not `CASCADE`. A category (or subcategory) used by a transaction cannot be deleted: the service answers **409** first (`category_ids_in_use()`), and the FK is the safety net. Deleting a user cascades to both `categories` and `transactions` in one statement; with `NO ACTION` the FK check runs at the end of the statement, after both cascades, so it succeeds on SQLite and Postgres (with `RESTRICT`, Postgres checks immediately and the result could depend on cascade order). There is no ORM back-reference from `Category` to its transactions, so the ORM never nulls `category_id` on delete.
- **Salary (§4.4):** a salary is an income transaction with `gross_amount` set. Effective deduction rate = `(gross − net) / gross`, computed and returned by the API (not stored). Totals and simulations always use `amount` (net).

### `category_amounts` (planned, M9)

| Column | Type | Notes |
| --- | --- | --- |
| user_id | FK | |
| category_id | FK → categories | top-level; its `kind` gives income or expense |
| subcategory_id | FK → categories, nullable | child of `category_id` |
| amount | numeric(12,2) | `> 0`, net, valid for every month |
| note | varchar(500), nullable | |

- One row per (`user_id`, `category_id`, `subcategory_id`): unique, with a partial unique index for the NULL subcategory case (as `categories` does). A second create for the same row updates it.
- Dashboard, `/categories/totals`, the delete guard and `avg_monthly_expenses` add these amounts to the transactions; the exact months-in-period rule and the endpoints are specified by the M9 issues and written here when implemented.

### `investments`

| Column | Type | Notes |
| --- | --- | --- |
| user_id | FK | |
| name | varchar(100) | |
| type | enum(`stock`, `fund`, `etf`, `crypto`, `deposit`, `real_estate`, `other`) | |
| platform | varchar(100), nullable | free text, optional; `NULL` = no platform (e.g. real estate, a deposit held directly) |
| amount_invested | numeric(14,2) | `≥ 0` |
| current_value | numeric(14,2) | `≥ 0`, updated manually |
| value_updated_at | date | date of the last manual update |

- `type` is stored like `categories.kind`: a string (non-native enum, `stock` / `fund` / `etf` / `crypto` / `deposit` / `real_estate` / `other`, the `InvestmentType` enum) with the CHECK `ck_investments_type`, so Postgres needs no `CREATE TYPE`.
- CHECK constraints: `ck_investments_amount_invested_non_negative` (`amount_invested >= 0`) and `ck_investments_current_value_non_negative` (`current_value >= 0`).
- Index: `ix_investments_user_id` on `user_id`. Deleting a user deletes their investments (`ON DELETE CASCADE`); there is no ORM back-reference from `User`.
- `platform` is optional: `NULL` means no platform. How the API turns an empty value into `NULL` is defined with the endpoints (§6).

Gain/loss (`current_value − amount_invested`) and gain % (`gain / amount_invested`, `null` if the amount invested is 0) are computed, not stored.

## 5. Authentication and authorization

- **Register:** `POST /api/auth/register` validates the email (stored lowercase, so `A@B.com` = `a@b.com`) and a password of 8 to 128 characters (422 outside that range; the upper bound protects Argon2), hashes it with Argon2, creates the user, seeds the default categories (plan.md §4.2) in the same DB transaction, and logs the user in. If seeding fails, nothing is committed.
- **Login:** verifies the hash and issues a JWT (`sub` = user id, `exp` = `ACCESS_TOKEN_DAYS`, default 7 days) signed with HS256 using `JWT_SECRET`. Tokens are decoded with a 5-second leeway for clock skew (applies to both `iat` and `exp`).
- **Cookie:** `access_token`, `HttpOnly`, `SameSite=Lax`, `Secure` in production (`COOKIE_SECURE`), `Path=/api`, `Max-Age` = `ACCESS_TOKEN_DAYS`. The token is never readable from JavaScript, so it is not exposed to XSS.
- **Logout:** clears the cookie.
- **Same origin:** in development Vite proxies `/api` to FastAPI. In production the backend serves the built frontend, or both sit behind the same domain. This avoids CORS and third-party cookie issues.
- **CSRF:** `SameSite=Lax` plus requiring `Content-Type: application/json` on every `POST`/`PUT`/`PATCH`/`DELETE` request, including body-less ones such as logout; anything else returns **415**. The frontend `apiFetch` always sends the header on these methods.
- **Authorization:** a `current_user` dependency guards every router except auth. Every query filters by `user_id`. Fetching another user's resource returns **404** (not 403, so the API does not reveal that the resource exists). Foreign keys sent in a body (e.g. `category_id`) are checked to belong to the current user.
- Login errors return a generic message ("Invalid email or password").
- **Rate limiting:** `POST /api/auth/login` and `POST /api/auth/register` are limited per client IP by an in-memory sliding-window counter (`app/ratelimit.py`, one counter per scope). Defaults: 10 login and 5 register attempts per 60 s (`RATE_LIMIT_LOGIN_ATTEMPTS`, `RATE_LIMIT_REGISTER_ATTEMPTS`, `RATE_LIMIT_WINDOW_SECONDS`; `0` disables a limit). Every attempt counts, and the check runs before the password is verified, so a correct password is also rejected once limited. Over the limit the API answers **429** `{"detail": "Too many attempts. Try again later."}` (same for any email) with `Retry-After` in whole seconds (>= 1). The client IP is the socket peer, or, with `TRUSTED_PROXY_COUNT=N > 0`, the Nth entry from the right of `X-Forwarded-For` (the left side is client-controlled), falling back to the peer if the header is missing or too short. The counter is per process (run a single worker) and resets on restart.

## 6. API

Prefix `/api`. JSON in and out. Money fields are serialized as **strings** (`"1234.50"`) so precision survives JSON. Errors use FastAPI's standard shape (`{"detail": ...}`), with 422 for validation errors.

### Auth

| Method | Path | Description |
| --- | --- | --- |
| POST | `/auth/register` | `{email, password}` → **201** + `UserRead`, sets the cookie; **409** if the email exists |
| POST | `/auth/login` | `{email, password}` → **200** + `UserRead`, sets the cookie; **401** "Invalid email or password" |
| POST | `/auth/logout` | **204**, clears the cookie |
| GET | `/auth/me` | **200** + `UserRead` (`401` if not logged in) |

`UserRead` is `{id, email, created_at}`. The password hash and the token never appear in a response body.

### Categories

| Method | Path | Description |
| --- | --- | --- |
| GET | `/categories?kind=` | **200** + `list[CategoryTreeNode]`: the user's top-level categories ordered by id, each with its `subcategories` ordered by id. Without `kind` both kinds are returned; `kind` other than `income` / `expense` is **422** |
| GET | `/categories/totals?from=&to=` | `from` and `to` required dates (inclusive; missing, malformed or `from > to` is **422**) → **200** + `list[CategoryTotals]`: one entry per top-level category of the user (both kinds, ordered by id) `{category_id, total, subcategories: [{id, total}]}`, totals as 2-decimal strings (`"0.00"` when empty). A category total is its direct transactions plus its subcategories' in the period; a subcategory total is its own transactions. Declared before `/categories/{id}` |
| POST | `/categories` | `CategoryCreate {name, kind, parent_id?}` → **201** + `CategoryRead`. **404** if `parent_id` does not exist or belongs to another user; **422** if the parent is a subcategory (max two levels) or has a different `kind`; **409** on a duplicate name |
| PATCH | `/categories/{id}` | `CategoryUpdate {name}` (rename only; any other field is **422**) → **200** + `CategoryRead`; **404**, **409** on a duplicate name |
| DELETE | `/categories/{id}` | **204**, deletes the category and its subcategories; **404**; **409** `"This category or one of its subcategories has transactions"` and nothing is deleted |

`CategoryRead` is `{id, name, kind, parent_id}` (`parent_id` is `null` for a top-level category); `CategoryTreeNode` adds `subcategories: list[CategoryRead]`. Request bodies reject unknown fields (422). `name` is stripped at both ends and must then be 1–100 characters (422 otherwise). A category id that does not exist or belongs to another user is **404** `"Category not found"`.

Duplicates are **409** `"A category with this name already exists at this level"`, compared case-insensitively (SQL `lower()`) on the trimmed name: among the user's top-level categories of the same `kind`, or among the subcategories of the same parent. Renaming a category to its own name or changing only its case is allowed. A unique-constraint race on commit is also returned as 409. The "has transactions" check is `category_ids_in_use()` in `app/services/categories.py`: a category is in use when any of the user's transactions references it or one of its subcategories, as `category_id` or `subcategory_id` (a single `EXISTS` query). Deleting a top-level category checks it and all its subcategories; deleting a subcategory checks only that subcategory. If a transaction is created between the check and the delete, the FK violation on commit is rolled back and reported as the same 409.

### Transactions

| Method | Path | Description |
| --- | --- | --- |
| GET | `/transactions?from=&to=&type=&category_id=&subcategory_id=&page=&page_size=` | **200** + `TransactionPage {items, total}`; **422** on bad query parameters |
| POST | `/transactions` | `TransactionCreate` → **201** + `TransactionRead`; **404**, **422** |
| GET | `/transactions/{id}` | **200** + `TransactionRead`; **404** |
| PATCH | `/transactions/{id}` | `TransactionUpdate` (partial) → **200** + `TransactionRead`; **404**, **422** |
| DELETE | `/transactions/{id}` | **204**, no body; **404** |

All five need the cookie (**401** `"Not authenticated"`); `POST`/`PATCH`/`DELETE` with a non-JSON `Content-Type` are **415** (§5). A transaction id that does not exist or belongs to another user is **404** `"Transaction not found"`; a non-integer id is 422.

**Schemas.**

- `TransactionCreate {type, date, amount, gross_amount?, category_id, subcategory_id?, note?}`: `type` is `income` / `expense`, `date` an ISO date (`YYYY-MM-DD`, future dates allowed); `gross_amount`, `subcategory_id` and `note` default to `null`.
- `TransactionUpdate`: the same fields, all optional. Omitted fields are unchanged, an explicit `null` clears `gross_amount`, `subcategory_id` or `note`, and an explicit `null` for `type`, `date`, `amount` or `category_id` is 422. `{}` is 200 and changes nothing.
- `TransactionRead {id, type, date, amount, gross_amount, deduction_rate, category_id, category_name, subcategory_id, subcategory_name, note, created_at, updated_at}`. The names save the list UI extra requests; `subcategory_*` are `null` without a subcategory.
- `TransactionPage {items: list[TransactionRead], total}`: `total` counts the rows matching the filters before pagination.
- Request bodies reject unknown fields (422).

**Money.** Requests send decimal strings. `amount` and `gross_amount` must be `> 0`, have at most 2 decimal places (`"10.5"` and `"10"` are fine, `"10.123"` is 422) and fit `NUMERIC(12,2)` (max `9999999999.99`); `NaN`, `Infinity` and non-numeric strings are 422. Responses always return them as strings with exactly 2 decimals (`"10.50"`). `deduction_rate` is `(gross_amount − amount) / gross_amount` computed with `Decimal`, quantized to **4 decimals half up** and returned as a string (`"0.2000"`, i.e. 20 %; `"0.0000"` when gross equals net); it is `null` without `gross_amount` and is not stored (`compute_deduction_rate()` in `app/services/transactions.py`).

**Note.** Trimmed at both ends (inner whitespace kept); empty or whitespace-only is stored as `null`; more than 500 characters after trimming is 422.

**Validation order** (create, and PATCH on the merged result of the stored row plus the patch):

1. Schema errors → 422 (FastAPI's list-shaped `detail`).
2. `category_id` or `subcategory_id` that does not exist or belongs to another user → **404** `"Category not found"`.
3. Domain rules → **422** with a string `detail`:
   - `"The category must be a top-level category"`;
   - `"The category kind must match the transaction type"`;
   - `"The subcategory must be a subcategory of the category"` (also when it equals the category);
   - `"Only income transactions can have a gross amount"`;
   - `"The gross amount must be greater than or equal to the amount"`.

The subcategory is optional even when the category has subcategories. A rejected PATCH leaves the row unchanged, e.g. `{"type": "expense"}` on a salary with a gross amount is 422 while `{"type": "expense", "gross_amount": null, "category_id": <expense category>}` is 200, and changing `category_id` while the stored subcategory belongs to another category is 422 unless the body also sets `subcategory_id`.

**List query parameters.** All optional and combined with AND, always restricted to the current user:

- `from`, `to`: ISO dates, inclusive; `from` later than `to` is **422** `"'from' must be on or before 'to'"`; `from == to` is one day.
- `type`: `income` / `expense` (anything else 422).
- `category_id`: matches the transaction's top-level category, so it includes rows on its subcategories; `subcategory_id`: matches the subcategory. An id that does not exist, belongs to another user, or (for `category_id`) is a subcategory matches nothing: **200** `{"items": [], "total": 0}`, never 404.
- `page`: 1-based, default 1, `≥ 1`. `page_size`: default **50**, `1–100`. A page past the end is 200 with empty `items` and the real `total`.
- Order: `date` desc, then `id` desc. Category names are loaded with `selectinload` (no N+1).

### Investments

| Method | Path | Description |
| --- | --- | --- |
| GET | `/investments` | **200** + `InvestmentList {items, totals}`: all the user's investments with computed gain/loss, plus the portfolio totals |
| POST | `/investments` | `InvestmentCreate` → **201** + `InvestmentRead`; **422** |
| GET | `/investments/{id}` | **200** + `InvestmentRead`; **404** |
| PATCH | `/investments/{id}` | `InvestmentUpdate` (partial) → **200** + `InvestmentRead`; **404**, **422** |
| DELETE | `/investments/{id}` | **204**, no body; **404** |

All five need the cookie (**401** `"Not authenticated"`); `POST`/`PATCH`/`DELETE` with a non-JSON `Content-Type` are **415** (§5). An investment id that does not exist or belongs to another user is **404** `"Investment not found"`; a non-integer id is 422.

**Schemas.**

- `InvestmentCreate {name, type, platform?, amount_invested, current_value, value_updated_at?}`: `type` is one of `stock`, `fund`, `etf`, `crypto`, `deposit`, `real_estate`, `other` (`InvestmentType`; anything else 422); `platform` defaults to `null`; `value_updated_at` is an ISO date (`YYYY-MM-DD`) that may be omitted (see below) but not sent as `null` (422).
- `InvestmentUpdate`: the same fields, all optional. Omitted fields are unchanged, an explicit `null` (or `""`) clears `platform`, and an explicit `null` for `name`, `type`, `amount_invested`, `current_value` or `value_updated_at` is 422. `{}` is 200 and changes nothing. A rejected PATCH leaves the row unchanged.
- `InvestmentRead {id, name, type, platform, amount_invested, current_value, value_updated_at, gain, gain_pct, created_at, updated_at}`.
- `InvestmentList {items: list[InvestmentRead], totals: PortfolioTotals}` and `PortfolioTotals {total_invested, current_value, gain, gain_pct}` (the dashboard `investments` block below, without `by_type`).
- Request bodies reject unknown fields (422). `name` is trimmed at both ends and must then be 1–100 characters.

**Platform.** Trimmed at both ends; omitted, `null`, empty or whitespace-only is stored as `null`; more than 100 characters after trimming is 422.

**Money.** Requests send decimal strings. `amount_invested` and `current_value` must be `≥ 0` (0 is valid), have at most 2 decimal places and fit `NUMERIC(14,2)` (max `999999999999.99`); `NaN`, `Infinity` and non-numeric strings are 422. Responses return money as strings with exactly 2 decimals (`"150.00"`, `"-50.00"`). `gain` = `current_value − amount_invested`; `gain_pct` = `gain / amount_invested` with `Decimal`, quantized to **4 decimals half up** and returned as a fraction string (`"0.1500"` = 15 %, `"-0.1000"`), `null` when `amount_invested` is 0. Neither is stored (`compute_gain()` / `compute_gain_pct()` in `app/services/investments.py`).

**`value_updated_at`.** "Today" is the **server's local date** (`today()` in `app/services/investments.py`, the single source tests replace). Future dates are allowed, as for transaction dates, so a browser whose local date is already "tomorrow" gets no false 422; the UI may always send the date explicitly.

- Create: the date sent, or today when omitted.
- PATCH with `current_value` and without `value_updated_at`: today, even if the value equals the stored one (the user confirmed it today).
- PATCH with `value_updated_at` (with or without `current_value`): the date sent.
- PATCH without either field: unchanged.

**Totals.** Summed with `Decimal` over **all** the user's investments: `total_invested`, `current_value`, `gain` = `current_value − total_invested`, `gain_pct` = `gain / total_invested` (4 decimals half up), `null` when `total_invested` is 0. With no investments the money fields are `"0.00"` and `gain_pct` is `null`. Totals are not stored, so they may exceed `NUMERIC(14,2)` (`compute_totals()`).

**Order.** `name` case-insensitive ascending (SQL `lower(name)`), then `id` ascending. No pagination or filters (a personal portfolio is small).

### Dashboard

| Method | Path | Description |
| --- | --- | --- |
| GET | `/dashboard?from=&to=` | **200** + `Dashboard`; **401**, **422** |

`from` and `to` are **required** ISO dates, inclusive on both ends (`from == to` is one day). Missing or invalid is **422**; `from` after `to` is **422** `"'from' must be on or before 'to'"`. Money is a string with 2 decimals, rates are fraction strings with 4 decimals.

Response:
- `income_total`, `expense_total`, `savings` (= income − expense, may be negative), `savings_rate` (= savings / income, 4 decimals half up, `null` if income is 0)
- `expenses_by_category`: `[{category_id, name, total, subcategories: [{id, name, total}]}]`, only categories with expenses in the period, sorted by `total` desc then `name` (subcategories likewise). Expenses without a subcategory are one entry `{id: null, name: "(none)", total}` inside that category's `subcategories`. Subcategory totals add up to the category `total`, and category totals to `expense_total`. The frontend uses this for the pie chart drill-down without a second request.
- `investments`: `{total_invested, current_value, gain, gain_pct, by_type: [{type, current_value}]}`: a snapshot of **all** the user's investments, independent of `from`/`to`, with the same totals as `GET /investments`. `by_type` has one entry per type held, sorted by `current_value` desc then `type`; with no investments the money fields are `"0.00"`, `gain_pct` is `null` and `by_type` is `[]`.

Logic in `app/services/dashboard.py` (`build_dashboard`, `compute_savings_rate`), aggregated in SQL with `GROUP BY`.

The frontend computes the period (current month by default, current year, or custom range) and sends `from` and `to`.

## 7. Simulator

Lives in `backend/app/simulator/` as pure functions that take and return dataclasses / Pydantic models. All arithmetic uses `Decimal`; results are rounded to 2 decimals only at the output.

### 7.1 Common inputs

- `starting_amount ≥ 0`
- `contribution ≥ 0`, `frequency ∈ {weekly: 52, monthly: 12, yearly: 1}` periods per year (`n`)
- `scenarios`: `{pessimistic, base, optimistic}` annual return rates (e.g. `0.03`, `0.05`, `0.07`)
- `inflation_rate` (annual, e.g. `0.02`)
- `current_age`, `avg_monthly_expenses`

### 7.2 Conventions

- Periodic rate from an annual rate: `r_p = (1 + r)^(1/n) − 1` (compound-equivalent, so 12 months at `r_p` equals exactly `r` over a year).
- Contributions are made at the **end** of each period.
- Real value (today's dollars) at time `t` years: `nominal / (1 + inflation)^t`.
- Each scenario is computed independently with the same inputs.

### 7.3 Mode A — Accumulation

Input: `horizon_years` (1–60).
Iterate period by period: `balance = balance × (1 + r_p) + contribution`.
Output per scenario, for each year `0..horizon`: `{year, age, nominal, real, total_contributed}`. Also returned: `years_of_expenses_covered = real_final / (avg_monthly_expenses × 12)`.

### 7.4 Mode B — Goal

Input: `target_amount` (in today's dollars), `years`, and a flag `target_is_real` (default `true`, so the target is inflated to the nominal value at the target date).
With `N = years × n` periods and `FV` = the nominal target:
- `r_p ≠ 0`: `PMT = (FV − PV·(1+r_p)^N) · r_p / ((1+r_p)^N − 1)`
- `r_p = 0`: `PMT = (FV − PV) / N`
- If `PMT ≤ 0`, the starting amount already reaches the goal: return `0` and `already_reached = true`.

Output per scenario: `required_contribution` (per period of the chosen frequency) and `total_contributed`.

### 7.5 Mode C — Withdrawal / retirement

Input: `retirement_age > current_age`, `withdrawal_mode ∈ {percent, fixed}`, `withdrawal_rate` (e.g. `0.03`) or `monthly_withdrawal` (in today's dollars), `end_age` (default 100).
1. **Accumulation phase** until `retirement_age`, as in Mode A.
2. **Withdrawal phase**, monthly until the money runs out or `end_age` is reached. The balance keeps growing at the scenario's monthly rate, and the withdrawal grows with inflation every year:
   - `percent`: first-year annual withdrawal = `withdrawal_rate × balance at retirement`, divided by 12, then indexed to inflation.
   - `fixed`: `monthly_withdrawal` in today's dollars, converted to nominal at retirement, then indexed to inflation.

Output per scenario:
- `balance_at_retirement` (nominal and real)
- `monthly_income` (in today's dollars)
- `expenses_coverage_pct = monthly_income_real / avg_monthly_expenses`
- `lasts_until_end = true/false`, plus `depletion_age` when it does not last
- yearly series `{age, nominal, real}` for the chart

**`avg_monthly_expenses` default:** the user's total expenses over the last 12 full months ÷ the number of months that have data (at most 12). Returns `0` if there is no data; the frontend then asks the user to enter a value.

### 7.6 Validation

Rates must be between −0.5 and 0.5 and horizons between 1 and 60 years. Withdrawal mode requires `retirement_age < end_age ≤ 120`. Out-of-range input returns **422**.

## 10. Configuration and local development

Backend environment variables: `DATABASE_URL` (default `sqlite:///./dev.db`), `ENVIRONMENT` (`development` default, or `production`: startup fails with a clear error if `JWT_SECRET` is the development default or shorter than 32 characters, or if `COOKIE_SECURE` is false), `FRONTEND_DIST_DIR` (default `../frontend/dist`, `/app/frontend/dist` in the Docker image; when the directory contains `index.html` the API serves it, otherwise nothing is mounted), `JWT_SECRET` (the development default is at least 32 bytes, as PyJWT recommends for HS256), `COOKIE_SECURE` (default `false` locally, must be `true` in production), `PORT` (read only by the Docker entrypoint, default 8000),  `ACCESS_TOKEN_DAYS` (default 7), `RATE_LIMIT_LOGIN_ATTEMPTS` (10), `RATE_LIMIT_REGISTER_ATTEMPTS` (5), `RATE_LIMIT_WINDOW_SECONDS` (60), `TRUSTED_PROXY_COUNT` (0; set to the number of reverse proxies in production, see §5).

## 11. Deployment (after the MVP works locally)

A single service: a multi-stage Dockerfile builds the frontend, and FastAPI serves `frontend/dist` as static files plus `/api`. Managed Postgres. Candidates on free tiers: Render or Fly.io (Postgres from Neon or the provider itself). Migrations run on deploy (`alembic upgrade head`).

Implemented in milestone 8 (issue #46): `Dockerfile` at the repo root (stage 1 Node 24 builds `frontend/dist`; stage 2 Python 3.12 slim installs the backend with `uv sync --locked --no-dev`, copies the built frontend to `/app/frontend/dist`, runs as a non-root user, has a `HEALTHCHECK` on `/api/health`). `backend/docker-entrypoint.sh` runs `alembic upgrade head` and then `uvicorn` on `$PORT`. `app/frontend.py` serves the built files with an `index.html` fallback for non-`/api` paths (`/assets/*` with a one-year immutable `Cache-Control`, everything else `no-cache`); unknown `/api/*` paths keep the JSON 404. The Postgres driver is `psycopg[binary]` (`DATABASE_URL=postgresql+psycopg://...`). CI adds a `backend-postgres` job (`postgres:17` service, `alembic upgrade head`, `alembic check`, the whole pytest suite) and a `docker` job (builds the image and smoke-tests `/api/health`, `/` and `/investments` against a throwaway Postgres container).
